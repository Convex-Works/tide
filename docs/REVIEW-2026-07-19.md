# klisi — Adversarial Review, 2026-07-19

Point-in-time review of the klisi codebase at commit `c7a9ff0` (end of Phase 5).
Covers security, correctness, and complexity across the Go server, the SvelteKit
client, the deploy stack, and CI.

> **Remediation status (2026-07-20):** all findings — 1 critical, 4 high, 9 medium,
> 1 low, and Q1–Q3 — are fixed, one commit per finding, each with a **Resolution**
> note below. `make check` green throughout.

**Methodology.** Two independent passes — a manual read of every server package
and the security-critical client paths, plus an independent automated review
(gpt-5.6-sol) — merged and deduplicated. Every finding below was confirmed
either at runtime or by reading the exact code path; nothing is repeated on
trust. The "Evidence" line states how each was checked.

## Bottom line

The foundations are sound: every mutating route has an ownership check, all SQL
is parameterized, presigned downloads are scoped and short-lived, LiveKit
webhooks are signature-verified, and state-changing routes carry CSRF headers.

klisi is **not production-safe yet**, for two structural reasons:

1. **Configuration fails open.** Secrets and `DEV_MODE` have working defaults and
   nothing refuses to boot on them, so a missing env var yields a running server
   with publicly-known secrets and an unauthenticated token endpoint — not a
   crash.
2. **Moderation and recording assume delivery guarantees LiveKit does not make.**
   Kick relies on token revocation that self-hosted LiveKit lacks; recording
   correctness rides entirely on a webhook LiveKit explicitly does not guarantee
   to deliver.

Several findings bite specifically because the next step is a Kubernetes staging
deploy behind an ingress. Those are called out.

## Critical

### 1. ✅ Configuration fails open — unauthenticated token endpoint and forgeable sessions

- **Location:** `server/internal/config/config.go:36-53`, `server/internal/httpapi/handler.go:88-90`
- **Claim:** `DevMode` defaults to `true`, so an unset `KLISI_DEV_MODE` in production
  registers `GET /api/dev/token`, which mints a valid LiveKit join token for **any**
  room and name — no session, no lobby, no room-existence check. Separately, every
  secret has a working default (`SessionSecret`, `LiveKitAPISecret`, S3 credentials)
  and nothing validates them at startup, so a missing env var yields a running server
  with publicly-known secrets: forged host sessions, room-admin JWTs, and self-signed
  webhooks all become possible. The bundled `deploy/livekit.yaml` ships the same
  public secret.
- **Failure scenario:** Deploy the binary to staging having set the OIDC and S3 vars
  but forgetting `KLISI_DEV_MODE=false`. Any anonymous client GETs
  `/api/dev/token?room=<victim-room>&name=x`, receives a join token, and connects to a
  private meeting — the entire lobby/auth model bypassed.
- **Evidence:** `envBool("KLISI_DEV_MODE", true)` read directly; dev route registration
  gated on `cfg.DevMode` read directly.
- **Fix:** Default dev mode to `false`. Add a startup check that refuses to boot outside
  an explicit dev profile when any secret is missing, weak, or equal to a shipped
  default.
- **Resolution:** ✅ Fixed. `KLISI_DEV_MODE` now defaults to `false`; secrets have no
  defaults outside dev mode, and `config.Load` refuses to start when any secret is
  missing, shorter than the minimum, or equal to a shipped dev value (all problems
  reported at once). `make dev` opts in explicitly; a warning banner is logged when
  dev mode is on. Covered by `config_test.go`; verified at runtime (bare start → exit 1).

## High

### 2. ✅ Kick is advisory — a removed guest can rejoin with the same token

- **Location:** `server/internal/moderation/handler.go:48-50`, `server/internal/lobby/handler.go:21,165`
- **Claim:** `RemoveParticipant` disconnects a guest but does not invalidate their JWT.
  The guest still holds a 10-minute admission token and can reconnect directly to
  LiveKit, never returning through klisi's lobby. Self-hosted LiveKit provides no hard
  token revocation.
- **Failure scenario:** Host ejects a disruptive guest. The guest's client (or a
  scripted one) reconnects with the cached token within the TTL and is back in the
  meeting. Moderation looks enforced but isn't.
- **Evidence:** Code path read; corroborated by LiveKit's documented token lifecycle
  (self-hosted removal does not revoke existing tokens).
- **Fix:** Maintain a server-side denylist of kicked `identity`+room and reject them in
  the admission path; and/or shorten the admission-token TTL substantially so the
  rejoin window is small.
- **Resolution:** ✅ Fixed. Kick now denylists the `room`+`identity` (before the
  RemoveParticipant RPC, so a racing rejoin is caught) for the admission-token TTL;
  the `participant_joined` webhook re-removes any denylisted identity on reconnect,
  shrinking the rejoin window to one webhook round-trip. The owner's own identity is
  never banned. Token TTL kept at 10 min (needed for legitimate reconnects); covered
  by `moderation/denylist_test.go` and a webhook-hook unit test.

### 3. ✅ Recording has no reconciliation — a missed webhook permanently bricks a room's recording

- **Location:** `server/internal/recording/webhook.go:39-56`, `server/internal/recording/handler.go:149-153`, `server/internal/store/schema.sql:33-35`
- **Claim:** Recording correctness depends entirely on the `egress_ended` webhook,
  whose delivery LiveKit explicitly does not guarantee. Miss one (klisi restart,
  network partition, egress crash) and the row stays `starting`/`recording`/`finalizing`
  forever. The partial-unique index `recordings_one_active_room_idx` then rejects every
  future recording for that room, and the active-status guard also blocks deletion — the
  room's recording is permanently wedged with no non-DB recovery. Compounding it, `Stop`
  writes `finalizing` **after** `StopEgress` returns, so an `egress_ended` (completed)
  event landing during that RPC gets regressed back to `finalizing`, then never repaired.
- **Failure scenario:** Host stops a recording; `egress_ended` completes the row in the
  same instant `Stop` runs; `Stop` overwrites `completed` → `finalizing`; no further
  event arrives; that room can never record again and the row can't be deleted.
- **Evidence:** Update ordering in `Stop` read directly; active-status set confirmed in
  `store.go:219` (`status IN ('starting','recording','finalizing')`) and the partial
  unique index confirmed in `schema.sql:33`.
- **Fix:** Reconcile active rows against `ListEgress` on startup and periodically, with an
  age-based terminal fallback. Make status transitions monotonic so a terminal state
  (`completed`/`failed`) can never be overwritten.
- **Resolution:** ✅ Fixed, three ways. (1) `UpdateRecordingByEgress` now enforces
  monotonic transitions in SQL — a stale downgrade is a silent no-op and terminal
  states are immutable. (2) `Stop` persists `finalizing` *before* the StopEgress RPC
  (the race is structurally gone), retries the RPC for already-finalizing rows, and
  reports success if the row went terminal mid-flight. (3) A reconciler
  (`recording/reconcile.go`, run from `main` at startup + every minute) compares
  active rows against `ListEgress`: finished egresses finalize the row, lost stops
  are re-issued, and egresses LiveKit no longer knows are failed after a 2-minute
  grace. Covered by store monotonicity tests and five reconciler/stop-race tests.

### 4. ✅ Room deletion strands recordings; the FK cascade is dead

- **Location:** `server/internal/rooms/handler.go:130-153`, `server/internal/store/store.go:72-81`, `server/internal/store/schema.sql:27`
- **Claim:** `DeleteRoom` runs a bare `DELETE FROM rooms` — it never inspects or stops
  active egress, and never removes S3 objects. The `ON DELETE CASCADE` declared on the
  recordings FK is inert because SQLite defaults `foreign_keys=OFF` and it is never
  enabled. So deleting a room (a) leaves any in-progress egress recording a room that no
  longer exists, and (b) strands both the recording rows and their S3 files permanently —
  the files are unreachable because recording auth requires the deleted room.
- **Failure scenario:** Owner deletes a room to "clean up." The MP4s remain in the bucket
  forever, uncounted and undeletable through the app; if a recording was in progress,
  egress keeps writing.
- **Evidence:** `PRAGMA foreign_keys` default of `0` confirmed at runtime against the
  modernc/sqlite driver; `DeleteRoom` body and the pragma list read directly (no
  `foreign_keys` pragma present).
- **Fix:** Enable `PRAGMA foreign_keys=ON` on open; make room deletion stop active egress
  and delete S3 objects before removing rows.
- **Resolution:** ✅ Fixed. `store.Open` now sets `PRAGMA foreign_keys=ON` (single
  connection, so it sticks — verified by a cascade test that fails with FK off).
  `DeleteRoom` refuses with 409 while a recording is active (leaner than stop-and-wait
  orchestration; the #3 reconciler guarantees stuck rows go terminal, so refusal can
  never brick deletion), removes every stored S3 object before touching rows (aborting
  if removal fails), then deletes the room with the now-live cascade taking the
  recording rows. Covered by three deletion tests.

### 5. ✅ Webhook reads an unbounded body before authenticating

- **Location:** `server/internal/recording/webhook.go:19`, `server/cmd/klisi/main.go:16-28`
- **Claim:** The pinned LiveKit receiver `io.ReadAll`s the request body **before**
  verifying the signature. klisi applies no `MaxBytesReader` or read deadline to the
  webhook route, and the server sets only `ReadHeaderTimeout`. An unauthenticated client
  can stream an arbitrarily large body and exhaust heap or hold connections open.
- **Failure scenario:** Anyone who can reach `/api/webhooks/livekit` (public by design)
  POSTs a multi-gigabyte body; memory climbs before the signature check ever runs.
- **Evidence:** Handler reads body via the receiver before any auth; server timeout
  config read directly; corroborated against the pinned receiver source
  (`protocol@v1.39.3` reads the full body up front).
- **Fix:** Wrap the webhook body in `http.MaxBytesReader` before the receiver; add a
  `WriteTimeout` and a body read deadline for non-SSE routes.
- **Resolution:** ✅ Fixed. The webhook body is capped at 1 MB via `MaxBytesReader`
  before the receiver runs (oversize → 413, tested). The server now sets
  `ReadTimeout`/`WriteTimeout` of 30 s for every route; the lobby SSE handlers clear
  their own connection deadlines via `http.ResponseController` at stream start, so
  streams are unaffected. (Per-write SSE deadlines land with #12.)

## Medium

### 6. ✅ Rate limiter collapses to one global bucket behind a proxy — breaks in Kubernetes

- **Location:** `server/internal/httpapi/ratelimit.go:104-109`
- **Claim:** `clientIP` uses only `RemoteAddr`, ignoring `X-Forwarded-For`. The Go server
  uses plain `ListenAndServe`, so behind a k8s ingress every request appears to come from
  the ingress pod's IP. All join / lobby-wait / login traffic then shares one bucket.
- **Failure scenario:** In staging, ten logins per minute across *all* users exhaust the
  shared login bucket and everyone else is denied. The per-IP control is simultaneously
  defeated (real client IPs are invisible) and turned into a self-inflicted DoS.
- **Evidence:** `clientIP` implementation read directly — no `X-Forwarded-For`/`Forwarded`
  parsing.
- **Fix:** Parse `X-Forwarded-For` only from a configured trusted-proxy allowlist; key the
  bucket on the resolved client IP.
- **Resolution:** ✅ Fixed. `KLISI_TRUSTED_PROXIES` (comma-separated CIDRs or bare IPs;
  invalid entries refuse startup) configures a `clientIPResolver`. With no trusted
  proxies the TCP peer is the client and X-Forwarded-For is ignored (spoof-proof by
  default); when the peer is trusted, XFF is walked right-to-left past trusted hops to
  the edge-observed client. Malformed headers fall back to the peer. Unit-tested for
  forgery, chains, and fallbacks.

### 7. ✅ Chat impersonation — sender-supplied name is trusted

- **Location:** `web/src/lib/rtc/room.svelte.ts:302-317`
- **Claim:** The receiver renders `decoded.name` (from the sender's own JSON payload)
  before falling back to the authenticated LiveKit participant name:
  `from: decoded.name || participant?.name || …`. A guest can publish
  `{name:"Host", …}` and have the UI attribute the message to the host.
- **Failure scenario:** A guest posts an authoritative-looking message as "Host". Note this
  is the exact bug class the original mirotalksfu server guarded against by re-verifying
  `peer_name` — the rewrite dropped that protection.
- **Evidence:** `receiveChat` read directly; payload `name` is preferred over
  `participant.name`.
- **Fix:** Drop `name` from the chat payload entirely; attribute strictly from
  `participant.name` / `participant.identity`.
- **Resolution:** ✅ Fixed. `ChatPayload` no longer carries a name; recipients
  attribute messages solely from the authenticated LiveKit participant
  (`participant.name || participant.identity`), whose name is fixed by the
  server-minted token.

### 8. ✅ Database WAL/SHM files committed to git

- **Location:** `.gitignore:2-3`
- **Claim:** `.gitignore` has `*.db` and a root-only `/data/`, but the database lives at
  `server/data/` and the WAL/SHM sidecars don't match `*.db`. As a result
  `server/data/klisi.db-wal` and `server/data/klisi.db-shm` are tracked; the WAL contains
  plaintext room names, slugs, IDs, and owner subjects.
- **Evidence:** `git ls-files` lists both files (confirmed).
- **Fix:** Ignore `server/data/` and `*.db-{wal,shm}`; `git rm --cached` the tracked
  files; scrub history if real data was ever committed.
- **Resolution:** ✅ Fixed. `.gitignore` now covers `server/data/`, `*.db-wal`, and
  `*.db-shm`; the tracked sidecars were removed from the index. History was inspected:
  the committed WAL contained only local dev-stack data (dev Dex accounts, test
  rooms), so no history rewrite is warranted.

### 9. ✅ Sessions cannot be revoked

- **Location:** `server/internal/auth/session.go:17,90-100`
- **Claim:** Sessions are self-contained HMAC cookies with a 7-day TTL. Logout only clears
  the caller's browser cookie, so a copied/stolen cookie stays valid elsewhere for up to a
  week, and there is no way to invalidate on credential compromise.
- **Evidence:** `Clear` only sets an expired cookie; no server-side session state exists.
- **Fix:** Shorten the TTL and add a server-side session version / revocation identifier
  checked on each request.
- **Resolution:** ✅ Fixed. Sessions now carry a random `sid`; logout writes it to a
  `revoked_sessions` table (pruned opportunistically) and every session read checks
  it, so a copied cookie dies with logout everywhere. Lifetime shortened 7d → 24h,
  bounding a stolen cookie even without explicit revocation.

### 10. ✅ Guest can be stranded in "waiting" forever

- **Location:** `server/internal/lobby/registry.go:138`, `web/src/routes/m/[slug]/+page.svelte` (lobby-wait handlers)
- **Claim:** Resolved requests are deleted after another TTL. If a guest's tab is suspended
  across that window and resumes, `/wait` returns 404; the meeting page wires no error
  handler on the EventSource, so it never leaves the "waiting" state.
- **Evidence:** `resolve` schedules removal via `time.AfterFunc(r.ttl, …)`; client wait
  handlers omit an `error` branch.
- **Fix:** Provide a durable terminal-status lookup, or handle EventSource failure with a
  bounded timeout and an explicit expired state.
- **Resolution:** ✅ Fixed (client-side option). `lobbyWait` distinguishes transient
  errors (EventSource retries itself) from fatal ones (`readyState === CLOSED`, e.g.
  the 404 after the request expired during a tab suspend) and the meeting page maps
  fatal stream death to the existing `expired` state, from which the guest can ask
  to join again.

### 11. ✅ Stable host identity breaks multi-tab / multi-device

- **Location:** `server/internal/lobby/handler.go:61`
- **Claim:** Every host joins as `host:<sub>`. LiveKit permits only one participant per
  identity, so opening a second tab (or rejoining before the old session times out)
  disconnects the first. The client handles only `PARTICIPANT_REMOVED`, so a
  duplicate-identity disconnect leaves the displaced tab stranded on the stage.
- **Evidence:** Host identity construction read directly; client disconnect handling
  covers only the removed reason.
- **Fix:** Add a per-connection nonce to host identities; route every terminal disconnect
  reason to an explicit recovery state.
- **Resolution:** ✅ Fixed. Host identities are now `host:<sub>:<nonce>` (moderation's
  owner protection matches the prefix, tested), so extra tabs no longer displace each
  other. The client routes every non-client-initiated terminal disconnect — duplicate
  identity, server shutdown, room closed — to a new `disconnected` recovery state with
  a Rejoin action and a reason-specific message.

### 12. ✅ Unbounded host SSE streams; no write timeout

- **Location:** `server/internal/lobby/handler.go:123-153`, `server/cmd/klisi/main.go`
- **Claim:** The host lobby route has no per-session/room stream cap, no write deadline, and
  no write-error handling; the server sets no `WriteTimeout`. A host opening many
  non-reading connections consumes file descriptors and can wedge goroutines blocked in
  heartbeat writes.
- **Evidence:** Handler loop read directly (heartbeat `Fprint` with no deadline); server
  config sets only `ReadHeaderTimeout`.
- **Fix:** Cap concurrent streams per session/room; use per-write deadlines and exit on the
  first write error.
- **Resolution:** ✅ Fixed. Streams are capped at 4 per host session+room and 4 per
  guest wait request (429 beyond that). Every SSE write — events and heartbeats —
  now carries a 10 s write deadline via `http.ResponseController` and the handler
  exits on the first write/flush error, so a non-reading client is torn down at the
  next heartbeat instead of wedging a goroutine.

### 13. ✅ Dev stack exposes unauthenticated services on all interfaces

- **Location:** `deploy/compose.yaml`, `deploy/livekit.yaml:14-15`, `web/vite.config.ts:7`
- **Claim:** During `make dev`, Redis is published with no auth, MinIO publishes a root
  account whose password is in the repo, LiveKit exposes its API with the public secret,
  and Vite binds the LAN (`host: true`). Anyone on the same network can manipulate storage,
  Redis, or LiveKit.
- **Evidence:** Port mappings and credentials read directly from the compose and config
  files.
- **Fix:** Drop unnecessary host mappings; bind management ports to `127.0.0.1`; generate
  per-install secrets. (`host: true` on Vite is required for the egress template in dev —
  scope it rather than removing it.)
- **Resolution:** ✅ Fixed. Redis's host mapping is removed entirely (only LiveKit talks
  to it, in-network); LiveKit's signal/API port, MinIO (S3 + console), and Dex now bind
  `127.0.0.1`. The media ports (7881/tcp, 7882/udp) intentionally stay open — browsers
  dial the advertised LAN `KLISI_NODE_IP` and ICE/SRTP require the token handshake.
  Remaining LAN listeners are Vite (`host: true`, required for the egress template —
  acknowledged above) and the Go dev server; both are dev-profile-only, and the shipped
  dev secrets are refused in production since #1, so per-install secret generation was
  not added.

### 14. ✅ CI executes an unpinned generator

- **Location:** `Makefile:17`, `.forgejo/workflows/ci.yml`
- **Claim:** `make gen` runs `github.com/gzuidhof/tygo@latest`, invoked by CI on every
  change. A new, broken, or compromised upstream release gains CI code execution and can
  fail unchanged commits. This also contradicts ARCHITECTURE.md §11, which specifies
  pinning tygo.
- **Evidence:** Makefile target and CI job read directly.
- **Fix:** Pin tygo to an exact version; update deliberately.
- **Resolution:** ✅ Fixed. `make gen` pins `tygo@v0.2.21`; regenerated output is
  byte-identical, so the pin lands with zero drift.

## Low

### 15. ✅ Dashboard recording poll can outlive the page

- **Location:** `web/src/routes/+page.svelte` (recording poll + `onDestroy`)
- **Claim:** `onDestroy` clears only the currently-scheduled timer. An in-flight
  `listRecordings` that resolves after teardown schedules a fresh timer, so a destroyed
  dashboard keeps authenticated polling every 3s while a recording is active or wedged.
- **Evidence:** Poll scheduling and cleanup read directly.
- **Fix:** Abort in-flight requests, or guard post-await scheduling with a destroyed flag
  and a current-room check.
- **Resolution:** ✅ Fixed. A `destroyed` flag (set in `onDestroy`) plus a
  current-room re-check after the await guard both result storage and poll
  rescheduling; a resolution landing after teardown or after switching rooms is
  dropped.

## Quality — overcomplexity, duplication, verbosity

- **Q1. HTTP plumbing duplicated across five packages.** `lobby`, `rooms`, `auth`,
  `moderation`, and `recording` each carry their own `writeError` / `writeJSON` / JSON
  decode helpers. They already differ — the 1 MB body cap exists in only some of them —
  and will drift further. Consolidate into one `internal/httpx` package.
  - **Resolution:** ✅ Fixed. `internal/httpx` now owns `WriteJSON`/`WriteError`/
    `DecodeJSON` (bounded, strict); every per-package copy is deleted. Responses are
    byte-identical.
- **Q2. Ownership check copy-pasted four times.** `lobby.requireOwner`,
  `moderation.requireOwner`, `recording.requireOwnerBySlug`, and
  `recording.requireOwnerByRecording` are the same "load room by slug, compare `OwnerSub`"
  logic. One shared helper (or middleware keyed on the `{slug}` path value) removes ~80
  lines and removes the risk of one copy diverging.
  - **Resolution:** ✅ Fixed. `httpx.RequireRoomOwner` replaces all four copies with the
    per-route 403 messages preserved. A small `auth/sessionctx` package carries the
    session context value so `httpx` and `auth` don't cycle (`auth.Session` remains the
    public alias).
- **Q3. Client ownership probe fetches the whole room list.** `m/[slug]` calls both `me()`
  and `listRooms()` and scans for the slug just to decide whether the viewer is the owner.
  Add an `is_owner` field to `roomInfo` (or a dedicated endpoint) and drop the list fetch.
  - **Resolution:** ✅ Fixed. `PublicRoomInfo` gained `is_owner` (set server-side from
    the session; capabilities remain server-enforced) and the meeting page dropped the
    `listRooms()` scan.

## What is solid

Not everything is a finding. These were checked and hold up:

- Every mutating route re-derives ownership server-side from the session; no route trusts a
  client-asserted role.
- All SQL is parameterized; no injection surface found.
- Presigned download URLs are owner-gated and expire in 5 minutes.
- LiveKit webhooks are signature-verified before the state machine runs (the body-size
  issue in #5 is orthogonal to signature verification).
- CSRF headers wrap all state-changing browser routes; the session cookie is HttpOnly,
  `SameSite=Lax`, and `Secure` under HTTPS.
- Token grants are correct: guests never receive `roomAdmin` or host metadata.

## Recommended remediation order

Sequenced so nothing dangerous reaches the Kubernetes cluster:

1. **Before any staging deploy:** #1 (config fails open) and #6 (proxy rate-limiter). These
   are the two that make a public deploy immediately unsafe.
2. **Recording robustness** (the flagship feature): #3 and #4, then #5.
3. **Moderation and integrity:** #2 (kick enforcement) and #7 (chat attribution).
4. **Hygiene, batchable:** #8, #9, #14, and the Q1–Q3 cleanups.
5. **Remaining medium/low** as capacity allows.
